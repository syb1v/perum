# Техническая передача проекта PERUM

**Дата:** 17 июля 2026 года  
**Назначение:** передача контекста следующему программисту  
**Основной диапазон изменений:** коммиты №151–175, `7b6f613..ace40db`

## 1. Что было целью цикла

Последний цикл был посвящён не добавлению отдельных экранов, а укреплению базовых
инвариантов продукта перед расширением mobile и offline-функций:

- разделить фактический урок, публикацию и срок домашнего задания;
- сделать статус выполнения ДЗ персональным, идемпотентным и version-safe;
- подготовить legacy-данные журнала к модели `LessonOccurrence`;
- заменить физическое удаление предметов и тем безопасным архивированием;
- укрепить discovery и mobile auth при смене домена или версии школы;
- закрыть уязвимости push installation, support relay и школьных новостей;
- сделать успешный CI обязательным условием автоматического релиза;
- спроектировать следующий этап dynamic mobile descriptor.

За диапазон №151–175 выполнено 25 коммитов, затронуто около 77 файлов. Основные
изменения находятся в `perum-core`, `perum-tenant`, `perum-web`, `perum-mobile`,
shared OpenAPI contracts и GitHub Actions.

## 2. Что реализовано

### 2.1. Новая семантика домашних заданий

У Homework теперь раздельно представлены:

- `assigned_occurrence_id` — урок, на котором задание выдано;
- `target_occurrence_id` — урок, к которому оно относится;
- `published_at` — момент публикации;
- `deadline_at` — точный timezone-aware срок.

Старые `due_date` и `occurrence_id` пока сохранены как compatibility path.
Deadline сам по себе не создаёт `LessonOccurrence`. Новое ДЗ без `published_at`
является черновиком и не показывается ученику. Legacy-задания без новых полей
остаются видимыми по старым правилам.

Teacher web умеет выбирать server-side occurrence, отдельно задавать target и
deadline, сохранять черновик или сразу публиковать задание. Student web отображает
задания по target occurrence и использует fallback для legacy-данных.

Основные файлы:

- `perum-tenant/app/modules/coursework/schemas.py`
- `perum-tenant/app/modules/coursework/service.py`
- `perum-tenant/app/modules/student/service.py`
- `perum-web/src/components/journal/HomeworkModal.tsx`
- `perum-web/src/components/journal/TeacherLessonModal.tsx`

### 2.2. Персональный статус выполнения ДЗ

Добавлены состояния `not_started`, `in_progress`, `completed` и endpoint:

```http
PUT /api/homework/{homework_id}/state
```

Мутация принимает стабильный `client_action_id`, ожидаемую `version` и новый
`status`. Реализованы optimistic locking, exact replay, защита от повторного
использования action ID для другой операции и унифицированный `409
VERSION_CONFLICT` с текущим server snapshot.

В mobile добавлены student route `/homework`, account-scoped SQLite outbox,
повторная отправка после восстановления сети или приложения и явный выбор при
конфликте: принять серверную версию либо повторить локальное изменение поверх
актуальной версии.

Основные файлы:

### 2.3. Occurrence backfill и защита legacy-данных

Добавлен двухфазный maintenance flow для `school_admin` и `director`:

```http
GET  /api/admin/maintenance/occurrence-backfill
POST /api/admin/maintenance/occurrence-backfill
```

Сначала строится preview с safe groups, ambiguity report и SHA-256
`plan_token`. Apply разрешён только для неизменившегося плана. Неоднозначные
данные не исправляются эвристически. Legacy Homework намеренно не угадывается по
`due_date`, потому что это может привязать задание не к тому уроку.

Backfill обрабатывает legacy `Grade`, `LessonTemplate` и `ControlWork`. Все выборки
и обновления ограничены школой. Для администратора добавлена web-страница preview,
подтверждения и применения.

Основные файлы:

- `perum-tenant/app/modules/academic/backfill.py`
- `perum-tenant/app/modules/school_admin/router.py`
- `perum-tenant/tests/unit/test_occurrence_backfill.py`
- `perum-web/src/app/admin/occurrence-backfill/page.tsx`

### 2.4. Архивирование предметов и тем

Физическое удаление `Subject` и `Topic` заменено soft archive:

- `is_archived`;
- `archived_at`;
- `archived_by`.

Архивирование предмета также архивирует его активные темы и отключает предмет от
биржи, но не удаляет историю. Восстановление предмета и тем выполняется отдельно.
Архивные сущности нельзя использовать в новых Homework, ControlWork, Schedule,
teacher assignments, LessonTemplate, Grade и LessonOccurrence.

Существующий `DELETE` теперь означает archive, а не physical delete. Это важное
поведенческое изменение API.

```http
GET    /api/admin/subjects?include_archived=true
DELETE /api/admin/subjects/{subject_id}
POST   /api/admin/subjects/{subject_id}/restore

DELETE /api/journal/topics/{topic_id}
POST   /api/journal/topics/{topic_id}/restore
```

Основные файлы:

- `perum-tenant/app/modules/school_admin/service.py`
- `perum-tenant/app/modules/journal/service.py`
- `perum-tenant/tests/unit/test_academic_archiving.py`

### 2.5. Discovery и mobile auth

Core discovery теперь:

- учитывает только активные доменные aliases организации;
- имеет отдельный IP rate limit для GET и POST;
- возвращает стабильный `descriptor_revision`;
- возвращает `cache_ttl_seconds`;
- меняет revision при изменении effective routing или contract.

Mobile сохраняет стабильный `schoolId`, revision, срок descriptor и compatibility.
После TTL выполняется rediscovery по UUID школы. Смена endpoint не требует нового
login. До первого authenticated tenant request на cold start и account switch
проверяются descriptor, identity и API compatibility.

Rotating refresh исправлен так, чтобы runtime state менялся только после
успешного атомарного сохранения нового refresh token в SecureStore.

Основные файлы:

- `perum-core/app/routers/public.py`
- `perum-core/app/schemas/public.py`
- `perum-core/app/core/ratelimit.py`
- `perum-core/tests/test_tenant_discovery.py`
- `perum-mobile/src/auth/descriptorCore.ts`
- `perum-mobile/src/auth/descriptorCore.test.ts`
- `perum-mobile/src/auth/AuthProvider.tsx`
- `perum-mobile/src/auth/TenantDescriptorProvider.tsx`

### 2.6. Push installation security

Installation UUID больше не считается доказательством владения. Mobile создаёт
отдельный 256-bit secret и хранит его в SecureStore, tenant сохраняет только
SHA-256 digest. Регистрация и revoke проверяют proof of possession. Неверный proof
или чужая школа получают generic `404`, чтобы не раскрывать существование записи.

Revoke требует заголовок:

```http
X-Installation-Proof: <installation-secret>
```

Основные файлы:

- `perum-tenant/app/modules/push/service.py`
- `perum-tenant/app/modules/push/router.py`
- `perum-tenant/tests/unit/test_push.py`
- `perum-mobile/src/push/installation.ts`

### 2.7. Безопасный relay обращений в поддержку

Восстановлена обязательная граница между platform support и пользователем школы:

```text
platform_admin -> Core -> org_admin relay -> tenant admin inbox
-> отдельный ответ school_admin/director -> requester
```

Ответ platform admin не попадает пользователю напрямую. Org admin формирует
идемпотентный relay, tenant сохраняет его как `admin_inbox`, а school admin или
director отдельно решает, что отправить пользователю.

Новый endpoint:

```http
POST /api/support/escalations/{ticket_id}/relay
```

Основные файлы:

- `perum-core/app/routers/support.py`
- `perum-core/tests/test_support_escalations.py`
- `perum-tenant/app/modules/support/escalation.py`
- `perum-tenant/app/modules/support/service.py`
- `perum-tenant/tests/unit/test_support.py`

### 2.8. Stored XSS в школьных новостях

экранированный plain text; legacy markup не выполняется как HTML.

### 2.9. CI, release и API contracts

Автоматический release теперь запускается через `workflow_run` только после
успешного CI и использует ровно тот SHA, который прошёл проверку. Тот же immutable
SHA применяется при checkout, тегировании образов и регистрации tenant release.

CI расширен следующими gates:

- полный Core pytest и tenant unit pytest;
- проверка единственной Alembic head;
- SQLite migration smoke;
- focused Homework/backfill/archive suites;
- shared package tests;
- web typecheck и production build;
- production dependency audit;
- mobile typecheck, unit tests, Expo config и Android/iOS export;
- OpenAPI regeneration/drift check;
- parse smoke workflow YAML.

Core и tenant OpenAPI обновлены, TypeScript-типы перегенерированы.

Основные файлы:

- `.github/workflows/ci.yml`
- `.github/workflows/release.yml`
- `packages/api-schema/openapi/core.json`
- `packages/api-schema/generated/core.ts`

## 4. Ключевые инварианты, которые нельзя нарушать

1. `LessonOccurrence` является идентичностью учебного события, а не просто датой.
2. Урок выдачи, целевой урок, публикация и deadline ДЗ являются разными понятиями.
3. Deadline не используется для автоматического угадывания occurrence.
4. Draft Homework не виден ученику.
5. Offline mutation обязана иметь стабильный `client_action_id` и version CAS.
6. Конфликт не разрешается silent last-write-wins.
7. Backfill выполняется только через preview и совпадающий `plan_token`.
8. Неоднозначные legacy-данные остаются в ambiguity report.
9. Исторические предметы и темы не удаляются физически.
10. Архивные сущности нельзя переиспользовать в новых учебных данных.
11. Все academic операции должны быть ограничены `school_id` на service/query
    уровне.
12. Mobile получает tenant URL только через Core и не строит его из slug.
13. Identity tenant определяется public UUID, а не hostname.
14. Descriptor проверяется до authenticated tenant traffic.
15. Core discovery никогда не получает tenant access или refresh tokens.
16. Capability не заменяет RBAC, policy и entitlement.
17. Platform response нельзя показывать школьному requester напрямую.
18. Installation UUID не является proof of possession.
19. Автоматически выпускается только SHA, успешно прошедший CI.

## 5. Что осталось незавершённым

### P0. Dynamic mobile descriptor

Коммит №175 содержит утверждённый план, но не реализацию. Главный следующий
документ: `docs/DYNAMIC_MOBILE_DESCRIPTOR_PLAN.md`.

Нужно реализовать:

- release manifest в Core;
- строгую schema v1 для compatibility и curated capabilities;
- resolver по `School.release_tag`;
- `schema_version` и dynamic `descriptor_revision`;
- deployment readiness snapshot;
- Core/Tenant schema parity;
- сохранение capabilities в mobile account;
- feature/provider gating до первого tenant request;
- ограниченный 24-часовой last-known-good grace period;
- blocked state после окончания grace;
- upgrade/downgrade и multi-account lifecycle tests.

Текущий fallback при временной недоступности Core не ограничен временем. Это
осознанный временный долг, который нужно закрыть в descriptor implementation.

### P0. Homework receipt atomicity

Сейчас изменение `HomeworkStudentState` и создание
`HomeworkStateReceipt` фиксируются отдельными commit. Возможен crash-window:
состояние уже изменено, receipt ещё не записан, а повтор запроса получает version
conflict вместо exact replay.

Перед расширением offline teacher journal нужно:

1. Объединить изменение state и receipt в одну транзакцию либо формально утвердить
   другую семантику.
2. Добавить тест потери ответа/сбоя между state и receipt.
3. Добавить настоящий concurrent first-transition test.

### Academic и offline

- обработать ambiguity report как операционный процесс;
- расширить multi-device conflict matrix;
- добавить durable read cursors social/support;
- добавить offline creation support tickets;
- затем добавить teacher Homework/topic mutations;
- только после отдельного conflict QA переходить к Grade и offline-журналу.

### Внешние блокеры

- production scanner для вложений ещё не выбран;
- реальная push delivery через провайдеров не реализована;
- не закрыты legal/product ADR по несовершеннолетним, moderation и retention;
- full mobile parity учителя, родителя и административных ролей не готова;
- billing/ЮKassa по новому плану требует отдельного большого цикла;
- credentials, DNS, signing и store rollout остаются внешней работой.

До scanner readiness capabilities вложений должны оставаться выключенными. До
реальной provider readiness так же должна оставаться выключенной push delivery.

## 6. Рекомендуемый порядок продолжения

1. Проверить и зафиксировать baseline CI для `ace40db`.
2. Реализовать strict shared descriptor schema и release manifest.
3. Добавить Core release resolver и включить contract в descriptor revision.
4. Добавить authenticated deployment readiness snapshot.
5. Унифицировать Core и Tenant descriptor schemas.
6. Реализовать mobile persistence, capability gating и 24-hour grace.
7. Покрыть lifecycle: cold start, resume, account switch, upgrade и downgrade.
8. Закрыть Homework state/receipt atomicity и conflict matrix.
9. Продолжить offline в порядке: read cursors, support ticket creation,
   teacher Homework/topics, затем Grade/journal.
10. Параллельно выбрать scanner, оформить ADR и подготовить provider credentials.

Dynamic descriptor необходимо выполнять по этапам из
`docs/DYNAMIC_MOBILE_DESCRIPTOR_PLAN.md`, не начиная с UI-флагов. Source of truth
сначала должен появиться в release manifest и Core resolver.

## 7. Проверки и уровень уверенности

В репозитории добавлены unit и integration tests для Homework, occurrence backfill,
academic archiving, push, support, discovery и mobile descriptor/outbox. CI
настроен на полный набор проверок, перечисленный выше.

В документации и истории коммитов нет сохранённого числового результата полного
прогона для `ace40db`, поэтому нельзя утверждать конкретное количество passed
tests. Перед следующим изменением рекомендуется проверить фактический GitHub CI
run этого SHA или повторить локальные проверки затронутых сервисов.
