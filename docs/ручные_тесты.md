# А. Ручные тесты: ДЗ (P1 #5) + Оценки с темой (P1 #6)

## Предусловия
- Развёрнутый tenant-стек школы (тестовая школа)
- Ученик `5А` класса, учитель с предметом «Математика» в `5А`, админ школы
- Создана хотя бы 1 тема предмета (страница `/teacher/topics`)
- Создано хотя бы 1 домашнее задание на сегодня/завтра с вложением

---

## Блок А1. Домашние задания (задача #5)

### A1.1. Учитель видит существующие ДЗ в модале урока
**Было:** всегда «Домашнее задание не задано» (stub `/teacher/homework` → `{"homework": []}`)

**Шаги:**
1. Учитель → Расписание → клик на урок Математики в `5А`
2. В модале — секция «Домашнее задание»

**Ожидаем:**
- Список ДЗ с `due_date` = сегодняшняя/выбранная дата
- Видны title, описание, вложения (📎 файл / 🔗 ссылка)
- Кнопка «Редактировать» открывает `HomeworkModal` с предзаполненными полями

### A1.2. Создание ДЗ из модала урока
1. В модале урока → «Задать» / «Добавить ещё»
2. Заполнить: заголовок, описание, срок сдачи (рабочий день по расписанию), вложение
3. Сохранить

**Ожидаем:** ДЗ появляется в списке модала сразу (loadData), ученик видит его в своём дневнике.

### A1.3. Вкладка «Работы» у учителя
**Было:** всегда пусто (stub `{"works": []}`)

**Шаги:** Журнал → вкладка «Работы» → фильтры класс/предмет

**Ожидаем:**
- Таблица со строками ДЗ («ДЗ») и контрольных работ («КР»)
- Колонки: Дата, Тип, Предмет, Класс, Тема/Описание
- Бесконечная прокрутка (`has_more`), клик → правая панель «Детали работы»
- Без ошибок в консоли

### A1.4. Лента активности учителя (профиль)
**Было:** всегда пусто (stub `{"homework": []}`)

**Шаги:** Профиль учителя (дашборд)

**Ожидаем:** блок «Недавняя активность» показывает до 5 последних ДЗ (title, дата, класс, предмет).

### A1.5. Контрольные работы у учителя
**Шаги:** `GET /api/teacher/control-works` (через админку или прямым запросом)

**Ожидаем:** реальный список контрольных работ школы (раньше stub). Созданные через `POST /control-works` работы появляются.

### A1.6. Ученик: просмотр ДЗ
**Шаги:** Ученик → Расписание → клик на урок

**Ожидаем:** ДЗ с title, описанием, вложениями, сроком с подсветкой (Сегодня/Завтра/Просрочено). Без поля «completed».

### A1.7. Ученик: вкладка «Работы»
**Шаги:** Ученик → вкладка «Работы» → фильтры

**Ожидаем:**
- Работы со статусом `pending` или `overdue` (если срок прошёл)
- **НЕ** должно быть статуса `completed` (поле убрано) — все невыполненные = `pending`

## Блок А2. Оценки с темой урока (задача #6)

### A2.1. Создание оценки с темой (регресс — работало)
1. Журнал → `5А` / Математика → клик на пустую ячейку ученика по дате
2. В `GradeModal` выбрать тему в `<select>` «Тема (необязательно)»
3. Поставить оценку, сохранить

**Ожидаем:** оценка создаётся, `topic_id` сохраняется в БД (`grades.topic_id`).

### A2.2. Просмотр оценки с темой (учитель)
**Было:** тема не показывалась (`get_grade` не возвращал `topic_id`/`topic_name`)

1. Клик на ячейку с оценкой, у которой есть тема → `ViewGradeModal`

**Ожидаем:** строка «Тема: <название>» между «Дата урока» и «Комментарий». Если тема не задана — строка отсутствует.

### A2.3. Редактирование темы оценки (учитель)
**Было:** тему нельзя было изменить (`UpdateGradeRequest` без `topic_id`)

1. `ViewGradeModal` → «Редактировать»
2. В `<select>` «Тема» сменить на другую / «Без привязки к теме»
3. Сохранить → открыть снова

**Ожидаем:** тема обновилась. Список тем загружается по `subject.id` из оценки.

### A2.4. Тема в тултипе ячейки журнала (учитель)
**Было:** тултип без темы

**Шаги:** Навести курсор на оценку с темой в сетке журнала.

**Ожидаем:** тултип: `Оценка (xвес) · Название темы: ДД.ММ.ГГГГ`. Для оценок без темы — без части ` · ...`.

### A2.5. Ученик: тема в модале урока
**Было:** тема не показывалась

1. Ученик → Расписание → клик на урок с оценкой, у которой есть тема

**Ожидаем:** под типом работы — строка с названием темы (серым цветом). Оценки без темы — без строки.

### A2.6. Ученик: тема в аналитике (журнал)
**Было:** тултип без темы

**Шаги:** Ученик → вкладка «Оценки» (запускает `AnalyticsDashboard`) → навести на оценку в таблице «Электронный журнал»

**Ожидаем:** тултип `Оценка (xвес) · Название темы`. Поля `topic` в `GradesResponse.grades` и `DiaryGrade` приходят с бэка.

### A2.7. API-проверка полей (опционально, прямые запросы)
- `GET /api/journal/grades/{id}` → поля `topic_id`, `topic_name`
- `GET /api/journal/{class_id}/{subject_id}` → в `students[].grades[]` есть `topic_id`, `topic_name`
- `GET /api/student/diary?week_offset=0` → в `diary.*.lessons[].grades[]` есть `topic`
- `GET /api/student/grades` → в `grades[]` есть `topic`
- `PUT /api/journal/grades/{id}` с `topic_id` → тема меняется

## Блок А3. Регресс / граничные случаи

### A3.1. Оценка без темы
Создать оценку с «Без привязки к теме» → проверить все 4 места отображения (A2.2, A2.4, A2.5, A2.6). Нигде не должно быть `null`/`undefined` в UI.

### A3.2. Удаление темы
Удалить тему на `/teacher/topics` (есть оценки с этой темой) → оценки остаются (`ON DELETE SET NULL`), `topic_id` = null, тема не отображается.

### A3.3. ДЗ на воскресенье / не по расписанию
Создать ДЗ с `due_date` в воскресенье → ожидать ошибку «Нельзя задавать ДЗ на воскресенье». На день без урока → «У этого класса нет урока...».

### A3.4. Права доступа
- Учитель НЕ ведёт предмет в классе → `POST /homework` и `POST /journal/grades` → 403
- `school_admin` / `director` → обходят проверку `_assigned`, могут создавать/редактировать/удалять чужие ДЗ и оценки
- Ученик → `GET /homework` возвращает только ДЗ своего класса (auto-подстановка `class_id`)

### A3.5. Пагинация «Работы»
Создать >50 ДЗ+КР → вкладка «Работы»: первые 50, прокрутка вниз подгружает следующие. `has_more` корректен.

# Б. Рекомендация по настройке OTA-обновлений на нодах

> ⚠️ **КРИТИЧНО ДЛЯ КОЛЛЕГИ:** без этих настроек обновления школ (тенантов) на
> нодах работать не будут. CI соберёт образ, но он не зарегистрируется в ядре,
> и org_admin не увидит кнопку «Обновить». Подробности — в
> [docs/RELEASING.md](RELEASING.md) раздел 6 и [docs/OTA_UPDATES.md](OTA_UPDATES.md).

## Что происходит сейчас (после каждого коммита в `main`)

`release.yml` через `paths-filter` определяет, что изменилось, и собирает
**только изменённые** образы → пушит в GHCR (`:git-<sha>` и `:latest`).

Три сервиса обновляются по-разному:

| Сервис | Как обновляется |
|--------|-----------------|
| **perum-core** + **perum-web** | Авто-деплой на прод по SSH, **если** `DEPLOY_ENABLED=true`. Иначе — вручную: `ssh root@87.232.119.17` → `cd /opt/perum/deploy` → `docker compose --env-file .env.prod -f docker-compose.core.yml -f docker-compose.prod.yml pull perum_core perum_web && up -d` |
| **perum-tenant** (школы) | **Opt-in OTA**: org_admin жмёт «Обновить» в орг-консоли (`/platform/org`). Ядро само обновляет стек школы (pull → stop/start app-контейнера, alembic upgrade, health-check, при сбое — авто-откат). Volume сохраняется. |

## Что нужно настроить в GitHub-репозитории

| Где | Имя | Тип | Зачем |
|-----|-----|-------|-------|
| Settings → Variables | `CORE_URL` | variable | URL ядра (`https://admin.<домен>`) — **включает шаг регистрации релиза** |
| Settings → Secrets | `RELEASE_PUBLISH_TOKEN` | secret | bearer для `POST /api/ci/release`. **То же значение** должно лежать в `deploy/.env.prod` (переменная `RELEASE_PUBLISH_TOKEN`) |
| Settings → Variables | `PUBLIC_BASE_DOMAIN` | variable | домен прода — для билда web-образа (домен вшивается в билд) |
| Settings → Variables | `DEPLOY_ENABLED` | variable | `true` — включает авто-деплой core+web по SSH (если не нужен — оставить пустым) |
| Settings → Secrets | `DEPLOY_SSH_HOST` | secret | хост прод-сервера (`87.232.119.17`) для SSH-деплоя |
| Settings → Secrets | `DEPLOY_SSH_USER` | secret | пользователь SSH (`root`) |
| Settings → Secrets | `DEPLOY_SSH_KEY` | secret | приватный SSH-ключ (с доступом к серверу) |
| Settings → Secrets | `DEPLOY_SSH_PORT` | secret | порт SSH (опц., по умолчанию `22`) |

## Пошаговая настройка

### 1. Сгенерировать `RELEASE_PUBLISH_TOKEN`
```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```
Положить одинаковое значение:
- в GitHub repo → Settings → Secrets and variables → Actions → New secret: `RELEASE_PUBLISH_TOKEN`
- в `deploy/.env.prod` на сервере: `RELEASE_PUBLISH_TOKEN=<то же значение>`
- пересоздать `perum_core` после правки `.env.prod`

### 2. Задать переменные
- `CORE_URL` = `https://admin.<ваш-домен>` (URL ядра, откуда org-консоль видит API)
- `PUBLIC_BASE_DOMAIN` = `<ваш-домен>` (для билда web-образа; домен вшивается в Next.js билд через `NEXT_PUBLIC_BASE_DOMAIN`)

### 3. (Опц.) Включить авто-деплой control plane
Если хотите, чтобы core+web сами катились на прод после push в `main`:
- `DEPLOY_ENABLED=true`
- Завести deploy-ключ (`ssh-keygen`), публичную часть — в `~/.ssh/authorized_keys` сервера, приватную — в секрет `DEPLOY_SSH_KEY`
- `DEPLOY_SSH_HOST`, `DEPLOY_SSH_USER` задать
- На сервере репо должно лежать в `DEPLOY_PATH` (дефолт `/opt/perum`) с `deploy/.env.prod`, где `CORE_IMAGE`/`WEB_IMAGE` = GHCR `:latest`, `*_PULL_POLICY=always`

### 4. Проверить
После push в `main`, меняющего `perum-tenant/**`:
1. Workflow `release.yml` должен собрать `perum-tenant:git-<sha>` и зарегистрировать релиз (в логах увидите `POST /api/ci/release → 201`)
2. В ядре (`/platform` → «Релизы») появится новый текущий релиз
3. В орг-консоли (`/platform/org`) у школ появится баннер «Доступно обновление → git-<sha>» с ченджлогом и кнопкой «Обновить»
4. org_admin жмёт «Обновить» → OTA, школа переходит в `updating → active`, при сбое — `failed`/`rolled_back`

## Если регистрация не настроена (резерв)

Образ всё равно лежит в GHCR. Релиз можно опубликовать вручную от platform_admin:
```bash
curl -X POST https://admin.<домен>/api/releases \
  -H "Authorization: Bearer <platform_admin_token>" \
  -H "Content-Type: application/json" \
  -d '{"version_tag":"git-<sha>","image":"ghcr.io/<owner>/perum-tenant:git-<sha>","changelog":"...","source_commit":"<sha>"}'
```
Ядро отклонит (409), если образ/коммит совпадает с текущим (защита от «пустых» OTA).

## Важные инварианты (не нарушать)

- **Релиз = строка в `releases` ядра** (`channel`, `version_tag`, `image`, `source_commit`, `changelog`, `is_current`).
- **Образ обязан быть из CI-сборки** (тег по `git-<sha>`), не выдумываться вручную.
- **OTA = opt-in**: ядро не обновляет школы само, только по кнопке org_admin.
- **Volume-preserving**: данные школы сохраняются при OTA.
- **Авто-откат**: при провале health-check после обновления ядро возвращает прежний образ.
